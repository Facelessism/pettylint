# PL006 — commented-code

**Category:** dead-code · **Default severity:** notice · **Default confidence:** medium or low
**Languages:** JavaScript, TypeScript · **Autofix:** not available

## Purpose

Conservatively detects comments that look like commented-out code, rather
than natural-language prose.

## Why it exists

Commented-out code tends to accumulate and rot: it's neither running code
nor useful documentation, and it's rarely deleted once it's been there a
while.

## How the heuristic works

PettyLint groups consecutive single-line comments (and each block comment)
into a single "comment block," then scores each line inside it for
code-like signals: braces/semicolons, assignment operators, common
keywords (`const`, `return`, `if (`, `import`, ...), call-expression shapes,
and arrow functions. A block is only flagged when:

- at least two of its lines each show at least one code-like signal
  (confidence: `medium`), or
- it is a single line with a strong combination of signals — at least
  three distinct kinds at once (confidence: `low`).

A single natural-language sentence, even one that mentions code-adjacent
words, will not accumulate enough signal to cross either threshold.

## Examples that trigger

```ts
// const user = getUser();
// if (user) {
//   return user;
// }
```

## Examples that do not trigger

```ts
// This handles authenticated users.
// See the README for usage examples.
// uses x
```

## Limitations

This is a heuristic, not a parser for comment contents — PettyLint does
not attempt to actually parse arbitrary comment text as code. It will miss
some genuinely commented-out code (false negatives) and, rarely, may flag
a comment that happens to read like code (false positives). When the
heuristic is noisy for a given codebase, narrow it further via
configuration (`commented-code: off`) rather than working around false
positives by hand.

This heuristic was tuned against a battery of realistic non-code comment
patterns — license headers, JSDoc, section dividers, changelog notes,
prose mentioning function names or containing an `=` sign — none of which
trigger a finding. Two specific false-positive sources found during that
process are guarded against explicitly: the bare English words "new" and
"else" no longer count as code-like signals unless they appear in their
actual code shapes (`new Foo(`, `} else`, `else {`, `else if`), and a
multi-line block needs a minimum combined signal strength, not just two
lines that each show one weak signal (e.g. two lines each containing a
bare `=`, as in "x = the input value").

## Suppression

```ts
// pettylint-disable-next-line commented-code
// const legacy = oldImplementation(); // kept for reference, remove after v3
```

## Autofix

Not provided. Deleting a comment based on a heuristic guess is exactly the
kind of "fix" that could destroy something the author meant to keep.
