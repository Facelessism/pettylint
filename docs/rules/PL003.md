# PL003 — empty-catch

**Category:** error-handling · **Default severity:** warning · **Default confidence:** high
**Languages:** JavaScript, TypeScript · **Autofix:** not available

## Purpose

Detects `catch` blocks with no statements, with or without a bound
parameter.

## Why it exists

An empty catch block silently discards the error. Whatever went wrong
disappears without a trace, which makes real failures invisible until
something downstream breaks in a more confusing way.

## Examples that trigger

```ts
try {
  work();
} catch {}

try {
  work();
} catch (error) {
}
```

## Examples that do not trigger

```ts
try {
  work();
} catch (error) {
  console.error(error);
}

try {
  work();
} catch (error) {
  throw error;
}

try {
  work();
} catch (error) {
  handle(error);
}
```

## Limitations

PettyLint does not evaluate whether the catch body's handling is *good* —
only whether it's empty. A catch block containing a single no-op statement
(e.g. `catch (e) { ; }`) is technically non-empty by this rule's
definition and will not be flagged; that's a deliberate narrowing to avoid
guessing at intent.

## Suppression

```ts
// pettylint-disable-next-line empty-catch
try {
  optionalStep();
} catch {}
```

## Autofix

Not provided. There's no mechanically safe rewrite: inserting a `throw` or
a log statement changes program behavior, which PettyLint's autofix policy
does not allow for a rule like this.
