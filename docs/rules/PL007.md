# PL007 — debug-pattern

**Category:** debugging · **Default severity:** notice · **Default confidence:** medium
**Languages:** JavaScript, TypeScript · **Autofix:** not available

## Purpose

Detects a small, explicit set of synchronous browser debugging dialogs:
`alert(...)`, `prompt(...)`, and `confirm(...)`.

## Why it exists

These globals block the main thread and are almost always used for local
debugging rather than production UX. Each one has a documented rationale;
this rule is intentionally kept small and is not a general style checker.

## Examples that trigger

```ts
alert("got here");
prompt("enter a value");
confirm("are you sure?");
```

## Examples that do not trigger

```ts
// alert("got here")            // inside a comment
pager.alert("got here");        // a method on some other object, not the global
```

## Limitations

Detection matches a bare identifier call (`alert(...)`, not
`window.alert(...)` or a method access on another object), to avoid
guessing at unrelated APIs that happen to share a name. `console.*`
methods are covered by PL001, not this rule, even though they're also
debugging-oriented.

## Suppression

```ts
// pettylint-disable-next-line debug-pattern
confirm("this is an intentional user-facing dialog, not debug code");
```

## Autofix

Not provided. These calls sometimes are the intended (if old-fashioned)
UX, so PettyLint reports them without assuming they should be removed.
