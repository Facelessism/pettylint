# Contributing to PettyLint

## Development setup

```bash
git clone <repository-url>
cd pettylint
pnpm install
```

Requires Node.js 20 or 22 and pnpm. No Docker, no GUI tools, no
platform-specific shell features — everything here works from a plain
terminal, including Termux on Android.

## Common commands

```bash
pnpm test           # run the Vitest suite
pnpm test:watch     # watch mode
pnpm typecheck      # tsc --noEmit
pnpm build          # build the library output and the bundled Action
pnpm pettylint .    # run the CLI against the current directory
pnpm pettylint --changed
pnpm pettylint baseline
pnpm pettylint --fix
```

## Project layout

```
src/
  index.ts        GitHub Action entry point
  core.ts         Analysis engine (Finding/Rule types, analyze())
  rules.ts        Built-in rules (PL001-PL007)
  github.ts       GitHub integration (PR context, annotations, summary)
  cli.ts          Local CLI
  config.ts       Configuration loading/validation
  diff.ts         Changed-range parsing/filtering
  baseline.ts     Baseline state
  format.ts       Output formatting (pretty/json/sarif/annotations/summary)
  languages/      Language adapters (JS/TS via the TypeScript Compiler API)
tests/            Vitest tests, one file per src module, plus fixtures/
```

The dependency direction is one-way: `rules.ts` never imports `github.ts`;
`core.ts` never imports `@actions/github`; the CLI and the Action both call
into `core.ts` rather than each re-implementing analysis.

## Adding a rule

A new built-in rule must include, in the same pull request:

1. **Implementation** in `src/rules.ts`, added to the `builtinRules` array.
2. **Tests** in `tests/rules.test.ts`: positive cases, negative cases, and
   edge cases (see the existing rules for the expected shape).
3. **Documentation** in `docs/rules/PL0XX.md` following the template used
   by the existing rule docs (purpose, examples that trigger, examples that
   don't, limitations, suppression example, autofix availability).
4. **Metadata**: a stable ID (`PL0XX` for built-ins), name, category,
   default severity, default confidence, and supported languages.
5. **A justification for false-positive behavior.** Before proposing a
   rule, answer the questions in the project's rule-quality bar:
   - What concrete behavior does it detect?
   - Why is that behavior worth reporting?
   - Can it be detected deterministically?
   - What are the known false positives and false negatives?
   - What severity and confidence are justified?
   - Can the source location be accurate?
   - Does an existing mature tool (ESLint, Semgrep, etc.) already cover
     this better? If so, it probably doesn't belong in PettyLint.

If you can't answer these clearly, the rule likely isn't a good fit.
PettyLint prefers ten useful findings over a hundred questionable ones.

## Adding an autofix

A rule may expose `fix: { description, edits(context, finding) }`, where
`edits` returns a single `{ start, end, text }` replacement (offsets into
the original source) or `null` when this instance can't be fixed with a
guaranteed behavior-preserving change. Add tests to `tests/fix.test.ts`
covering the safe case, every case where the fix must decline, CRLF
input, idempotence, and suppression. If you can't prove the fix is safe
in some syntactic position, return `null` for that position.

## Rule requirements

- `check(context)` must be deterministic: no network access, no GitHub
  access, no code execution, no dependence on the current time or on
  random values. The same source and configuration must always produce
  the same findings.
- Rules operate on the parsed AST (`context.source.sourceFile`) or, for
  comment-based rules, on `collectComments()`. Never regex-scan raw source
  text for code patterns — that's how PL001/PL002/PL006 avoid matching
  comments and string literals.
- Keep messages short, dry, and aimed at the code pattern, never at the
  person who wrote it.

## Fixture conventions

Small, focused fixture files live in `tests/fixtures/`. Keep them short —
a few lines demonstrating the behavior under test, not realistic
production files.

## Building the Action

```bash
pnpm build
```

This runs `tsc` for the library build and `@vercel/ncc` to bundle
`src/index.ts` into `dist/index.js`. **Commit the updated `dist/index.js`**
whenever a source or dependency change affects the Action — consumers of
the Action never run `pnpm install`, so the bundle must be self-contained
and up to date. Never hand-edit `dist/index.js`.

`dist/package.json` (containing `{"type": "commonjs"}`) must stay
alongside it and is regenerated by `pnpm build` — don't delete it. The
root `package.json` has `"type": "module"` (needed for the CLI/library),
but `@vercel/ncc` bundles to CommonJS `require()` syntax; without this
file, Node resolves `dist/index.js`'s module type from the nearest
`package.json` (the root one) and refuses to load a CommonJS file as ESM.
This file scopes `dist/` back to CommonJS.

## Pull request expectations

- `pnpm typecheck`, `pnpm test`, and `pnpm build` must all pass.
- New behavior needs tests; bug fixes should include a regression test.
- Rule IDs, the `Finding` schema, configuration keys, and documented CLI
  flags are public API — don't rename them casually. If a breaking change
  is unavoidable, document it and note the migration.
- Keep the architecture compact: don't introduce `src/utils/`,
  `src/services/`, or similar catch-all directories. If a file genuinely
  grows too large, extract a narrowly-named module for the specific
  responsibility that outgrew it.

## First-time release checklist

These steps need network access to the npm registry, so they are done once
on a developer machine (they cannot be generated offline):

1. `pnpm install` — creates `pnpm-lock.yaml`; commit it. CI uses
   `pnpm install --frozen-lockfile` and fails without it.
2. `pnpm typecheck && pnpm test` — must both pass under real Vitest.
3. `pnpm build` — produces `dist/index.js` (the bundled Action); commit it.
   CI fails if `dist/` is out of date relative to the sources.
4. The repository is `Facelessism/pettylint` (already set in
   `README.md` and `package.json`).
5. Tag the release (`v1`, `v1.x.y`) so `uses: <owner>/pettylint@v1` resolves.
   `action.yml` targets the `node24` Actions runtime (GitHub fully removed
   `node20` support on September 23, 2026); no change needed unless a
   future GitHub Actions runtime deprecation requires bumping it again.
