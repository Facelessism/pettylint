# PL002 — debugger

**Category:** debugging · **Default severity:** warning · **Default confidence:** high
**Languages:** JavaScript, TypeScript · **Autofix:** available (`pettylint --fix`)

## Purpose

Detects `debugger;` statements.

## Why it exists

A `debugger;` statement pauses execution in any JavaScript environment with
developer tools attached — including, potentially, production. It's almost
never intentional to ship.

## Examples that trigger

```ts
function handle() {
  debugger;
  return process();
}
```

## Examples that do not trigger

```ts
// debugger;             // inside a comment
const x = "debugger";    // a string, not a statement
```

## Limitations

None of note — `DebuggerStatement` is an unambiguous AST node kind, so this
rule has essentially no false positives or false negatives within valid
JavaScript/TypeScript syntax.

## Suppression

```ts
// pettylint-disable-next-line debugger
debugger; // intentionally left in a dev-only build script
```

## Autofix

`pettylint --fix` removes the statement, and the whole line when the
statement is the only thing on it. Removing `debugger;` cannot change
program behavior outside a debugging session, but the fix is still
deliberately narrow: it is only applied when the statement sits directly
in a statement list (a block, module, or `case`/`default` clause). It is
skipped for `if (x) debugger;` and `label: debugger;`, where deleting the
statement would change the program's structure. Findings suppressed with
an inline comment are never fixed, and with `--changed`/`--diff` only
findings on changed lines are fixed.
